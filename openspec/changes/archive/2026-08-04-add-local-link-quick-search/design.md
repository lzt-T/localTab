## Context

新标签页初始化时已经一次性加载全部 `CategoryInfo`，其中包含分类直属网址、文件夹及其网址；顶部 `SearchInput` 当前只管理搜索引擎选择、网页搜索和网址直达。该能力可以复用现有页面数据与打开网址回调，不需要访问数据库或增加共享状态。行为契约见 `specs/local-link-quick-search/spec.md`。

## Goals / Non-Goals

**Goals:**

- 在现有搜索框内增加本地网址派生、排序、展示和键盘选择流程。
- 保持搜索逻辑确定、无副作用，并与搜索引擎功能相互独立。
- 保持结果面板符合现有玻璃表面、响应式布局及组合框无障碍语义。

**Non-Goals:**

- 不检索描述、分类名或文件夹名，不实现模糊匹配。
- 不新增索引、持久化字段、全局 Store、Service 或第三方依赖。
- 不改变网页搜索、URL 直达、备份恢复或扩展权限行为。

## Decisions

### 使用页面已有分类数据派生结果

`NewTabApp` 将 `categories` 和现有网址打开回调传入 `SearchInput`。搜索框将分类网格顺序展开为带分类和可选文件夹上下文的临时结果，再执行匹配和排序。

选择该方案是因为数据已经在内存中且会随页面刷新更新。相比直接查询 IndexedDB 或新增 Store，该方案依赖更少、数据流更清晰，也不会产生第二份需要同步的搜索索引。

### 使用简单分级匹配

搜索函数将查询、标题和 URL 统一为小写，通过固定匹配等级表实现标题前缀、标题包含和 URL 包含的排序，并使用展开顺序作为同等级决胜条件。

相比引入模糊搜索库，该方案符合当前精确匹配范围，结果可预测且无需新增依赖。结果上限固定为 6，避免浮层过高和不必要的渲染。

### 将结果展示与搜索框状态分离

搜索框负责查询、焦点、高亮索引和键盘分发；纯搜索函数负责结果派生；独立结果组件负责列表渲染和鼠标交互。状态保持在搜索框局部，不进入全局 Store。

该拆分使搜索引擎菜单、快速搜索交互和纯匹配逻辑各自保持单一职责，同时避免为一次性能力增加 Hook 或 Service 层。

### 采用组合框键盘模型

输入框保留焦点，通过 `aria-activedescendant` 指向列表框中的当前选项；列表选项不进入 Tab 顺序。方向键循环选择本地结果和末尾网页搜索操作，Enter 执行当前项，Escape 清空并关闭。输入法组合期间忽略这些快捷键。

相比让焦点在结果按钮间移动，该方案保持输入连续性，并与可编辑组合框的预期交互一致。鼠标按下结果时阻止输入框失焦，确保点击事件执行前面板不会卸载。

## Risks / Trade-offs

- [每次渲染都会重新展开并匹配全部网址] → 当前数据为本地个人网址集合且最多渲染 6 条结果，先保持直接计算；仅在实际性能数据表明存在问题时再增加缓存或索引。
- [简单子串匹配无法容忍拼写错误] → 明确保持确定性匹配范围，未来若引入模糊搜索需作为独立规格变更评估排序和依赖。
- [搜索结果浮层可能与固定导航重叠] → 搜索容器在结果打开区域使用更高层级，面板宽度跟随搜索框并截断长文本。

## Migration Plan

该变更不涉及数据迁移。部署时随扩展前端资源一同发布；回滚时移除快速搜索组件与属性传递即可，现有持久化数据保持兼容。
