## Context

LocalTab 的业务数据存储在 IndexedDB 的 `category`、`link`、`linkGroup` 和 `system` 表中。分类主网格中的直属网址与文件夹共享连续的 `sort`，文件夹内网址另行排序。现有 JSON 恢复通过 `db.replaceAll` 使用跨表事务覆盖全部数据，但浏览器书签导入需要追加数据并保证失败时无部分残留。

当前 Chrome、Edge、Opera 清单分别维护，Brave 构建复用 Chrome 清单。现有必需权限为 `activeTab`、`search` 和 `favicon`；新增书签读取不能扩大安装时权限，也不能改变本地优先与最小权限承诺。

## Goals / Non-Goals

**Goals:**

- 将 `bookmarks` 作为运行时可选权限，并把权限请求绑定到明确的用户点击。
- 只读取一次浏览器书签树，在内存中完成转换与预览后释放权限。
- 将任意深度书签树稳定映射到现有两级 LocalTab 数据模型。
- 在不修改既有记录的前提下原子追加整个导入计划。
- 保持解析、转换、持久化和 React 界面的职责边界清晰。

**Non-Goals:**

- 不与浏览器书签双向同步，也不监听后续书签变化。
- 不通过书签 API 创建、更新、移动或删除浏览器书签。
- 不在首版支持合并到已有分类、HTML 文件导入或其他书签文件格式。
- 不更改 LocalTab 数据库版本、表结构或现有 JSON 备份格式。
- 不保存浏览器书签节点 ID、创建时间等同步元数据。

## Decisions

### 1. 使用可选权限并在读取后立即释放

在各浏览器清单的 `optional_permissions` 中声明 `bookmarks`。数据管理界面先展示用途说明，用户点击“授权并读取”时直接调用权限请求；授权前只检查权限请求与释放 API 是否可用，不以 `bookmarks` API 是否已暴露判断浏览器支持性。授权成功后重新获取浏览器扩展 API，检查并调用 `bookmarks.getTree` 读取完整书签树，并在树读取成功或失败后释放权限。

部分 Chromium 环境仅在可选权限获批后暴露 `bookmarks` API。如果授权前检查 `bookmarks.getTree`，会在浏览器实际支持该能力时误报“不支持”，并导致原生授权提示永远无法出现。因此能力检测必须遵循“检查权限 API → 请求权限 → 重新获取并检查书签 API → 读取书签树”的固定顺序。

立即释放而不是保留到写入完成，因为预览和持久化只依赖已经读取到内存的数据。这样权限持有时间最短，也使取消预览不会留下持续授权。替代方案是将 `bookmarks` 设为必需权限或长期保留权限，都会扩大安装、升级或日常运行时的授权范围。

### 2. 浏览器适配层只暴露只读能力

新增一个浏览器书签读取服务，集中封装能力检测、权限状态、请求、完整树读取和权限释放。能力检测分为授权前和授权后两阶段：授权前仅确认权限 API 可用，授权后重新获取扩展 API 并确认 `bookmarks.getTree` 可用。该服务的公开接口不提供任何写入浏览器书签的方法，从代码边界上约束只读承诺。

书签树节点使用项目内最小类型声明，只包含转换需要的 `id`、`title`、`url`、`children` 和可选的顶层类型信息。不同 Chromium 实现缺少顶层类型信息时，使用节点标题和树中位置回退，不依赖新版本专属字段。

### 3. 先构建纯内存导入计划

读取服务返回的树交给纯转换函数，生成包含新 `Category`、`LinkGroup`、`Link` 和跳过统计的导入计划。转换阶段生成新的 LocalTab ID、`parentId` 和连续 `sort`，但不访问数据库和界面状态。

转换规则如下：

1. 根节点下每个包含有效网址的顶层容器成为新分类。
2. 顶层容器直属网址成为分类直属网址。
3. 顶层容器以下的每个非空文件夹成为一个 LocalTab 文件夹。
4. 深层文件夹以相对顶层容器的完整路径命名，例如 `开发 / 前端 / React`。
5. 遍历使用源节点顺序；分类主网格按直属网址和首次遇到的文件夹生成统一 `sort`，文件夹内网址按深度优先顺序生成连续 `sort`。
6. 空标题使用域名或完整 URL 回退，非 HTTP(S) URL 被跳过。
7. 在每个计划分类内使用完整 URL 集合去重，首次出现的位置获胜。

相较把所有书签放进一个分类，顶层容器到分类的映射更接近浏览器原有组织。相较新增嵌套文件夹数据模型，路径展平不需要数据库迁移，也不扩大现有界面复杂度。

### 4. 始终创建新分类而不合并现有数据

转换前读取现有分类名称，为冲突名称追加本地化的“导入”后缀和递增序号。导入计划只包含新 ID，因此不会覆盖现有记录，也不需要复杂的逐项冲突选择。

首版不提供“合并到同名分类”。合并会引入跨现有文件夹的重复判定、排序位置和用户选择，显著扩大预览与回滚语义；新分类策略允许用户检查结果后自行移动内容或整体删除导入分类。

### 5. 增加跨业务表的原子追加方法

在数据库工具中增加只接收分类、网址和文件夹集合的批量追加方法。该方法在包含三个对象表的单个 `readwrite` 事务中执行所有 `add` 请求，不清空任何表，也不访问 `system` 表。使用 `add` 而不是 `put`，使意外 ID 冲突触发事务失败而非覆盖旧记录。

事务完成后界面刷新分类数据并显示实际导入统计；任何请求错误或事务终止都统一报告失败。替代方案是循环调用现有创建服务，但多个独立事务会在中途失败时留下部分导入数据。

### 6. 导入界面采用读取、预览、写入三阶段状态

数据管理中的浏览器书签区域维护以下有限状态：未开始、请求权限、读取中、预览、导入中、完成或错误。固定状态对应固定展示内容，使用状态到展示/行为的分发表，避免累积条件分支。

权限请求必须直接由按钮点击触发；在请求之前不插入异步确认弹窗。预览展示分类名称和各类数量，但不渲染完整书签树，避免大量书签造成界面卡顿。取消预览只清除内存计划。

## Risks / Trade-offs

- [浏览器原生提示包含“读取和更改书签”，而实现只读] → 在授权按钮旁提前解释只读取，并通过只读服务接口和不注册写入方法保持实现一致。
- [不同 Chromium 浏览器的根节点标题或顶层类型字段存在差异] → 以树结构和标题回退为基础，仅将顶层类型字段作为增强信息，并在目标浏览器中分别验证。
- [路径展平可能产生同名文件夹] → 使用完整相对路径作为名称；路径仍冲突时按首次出现顺序添加递增后缀。
- [大量书签转换或写入导致短暂等待] → 转换保持线性遍历，预览只展示汇总，持久化使用单个事务批量请求。
- [导入后的新分类数量较多] → 跳过不含有效网址的顶层容器，并在写入前明确展示将创建的分类列表。

## Migration Plan

1. 在各目标清单中增加可选权限后发布，不改变现有必需权限和数据库版本。
2. 旧用户升级后保持原授权状态；只有主动使用导入功能时才看到权限请求。
3. 若需要回滚，移除导入入口和可选权限声明即可；已经导入的数据仍是普通 LocalTab 分类和网址，无需迁移或清理。
